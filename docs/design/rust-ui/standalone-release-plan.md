# Standalone release first: implementation and acceptance plan

Date: 2026-10-22. Baseline inspected: `c09a822`. Status: design handoff, not implementation or a release-readiness claim.

## 1. Priority and authority

The delivery order is **complete local Linux + Windows application and installers → explicit local acceptance → persistent remote orchestration → actual UI-to-worker acceptance**. Local includes all hint routes, guided selection/tracking, movie sources, output delivery and persistence. The previous deferral of hints and video inputs is superseded. Existing remote code can remain, but new remote/service development must wait for gate L below.

Keep the selected Batch Board → Media / Hint / Key / Review / Deliver pages and the persistent seven-node graph. Reuse the Rust UI and Python/PyTorch engines; a Python-free rewrite, new compositor, new web framework, arbitrary graph engine and intra-clip distribution are outside this release. Local operation needs no SSH server, LAN, Tailscale, network listener or boot service. Internet is used explicitly to obtain/repair installation assets, never as an inference dependency once installed.

This plan changes sequencing in `ai-implementation-brief.md` and the old R0–R6 ordering. `range-output-contracts.md` remains authoritative for inclusive range confinement, source identity, frozen output paths, collisions and Resume. Preserve the selected workflow/preset semantics in `selected-design.md`; old code-fact documents describe their inspection date, not necessarily today's native implementation. This task changes only this document. No tests, model downloads, remote operations, OS changes or commits were performed for it. All inspection commands were short; subsequent inspection commands were explicitly bounded by `timeout 15s`.

Implementation roles from this brief: GLM handles coding and the separate model/install audit; Sol provides fallback planning/review; Flash handles visual review. This document does not start another audit or delegated task.

### Reuse with care

- Keep `InferenceParams`, `OutputConfig`, source stems, `RangeIdentity`, manifest ownership/completeness and atomic no-clobber publication as the shared contracts. Do not change Qt's whole-clip Key behavior incidentally; native confined-range behavior already has its own entry point.
- Keep one scheduler in Rust and one GPU job at a time per worker. Existing Python pipeline methods can be called through a small worker job adapter; do not also submit to Qt's `GPUJobQueue`.
- Existing guided methods require extracted sequences. Normalize movie sources and companion hint videos before invoking them. Preserve the original file and source frame identity.
- Do not directly expose destructive legacy hint behavior: `run_sam2_track` removes old mask images and then removes AlphaHint; VideoMaMa also removes prior alpha files. Generate into app-owned staging and publish a completed, validated hint set recoverably, retaining the previous usable hint on failure/cancel.
- `stitch_video` assumes a filename pattern, counts a directory and uses FFmpeg `-y`. A new Deliver adapter must select the exact manifest-backed range, handle gaps/custom names, write a temporary destination and preserve an existing deliverable on failure. Reuse the encoder/progress/cancel code rather than blindly calling it on an arbitrary output folder.

### Download, validation and offline behavior

1. **Install:** choose app/model/scratch locations → driver/runtime and per-volume space preflight → show complete download list/terms → download in dependency order with progress, cancel and resume → hash/config/import validation → write installation receipt → mark Ready only after the complete required profile succeeds. Asset download failure cannot produce a success summary. Handle gated access explicitly; keep credentials out of logs/settings/catalogs.
2. **Startup:** read receipt and cached validation records locally; compare catalog version, path, size and modification identity. Rehash missing/changed/unverified files, not tens of GB on every launch. Full verification is explicit in Settings and required after import/repair. Unchanged valid files trigger no metadata request, download or retry loop. Unverified/changed assets cannot advertise Ready before validation finishes.
3. **Settings → Models & runtime:** list each workflow/variant, dependency readiness, installed/expected revision, size, location, validation result and error; provide Install missing/Resume, Verify, Repair and Import existing cache/offline bundle. Move model storage through a validated copy then atomic preference switch; preserve the old copy until success. Block mutation of assets in active use; do not silently hot-swap a running model.
4. **Failure/cancel:** keep verified assets and resumable partials separate; never load `.part` files. Single ownership per artifact, atomic publish after hash validation, bounded retries/backoff, visible stalled/auth/proxy/disk/checksum errors. Resume only when source revision/identity agrees; retain compatible bytes and restart only the invalid artifact. Quarantine corrupt finals; cancellation must reach a terminal state and release ownership.
5. **Inference:** resolve explicit local paths and local-only loading; remove hidden network fallback from SAM/HF/torch.hub/BiRefNet/MatAnyone2 and any foundation loader. A missing model yields an actionable Models page link. Offline launch, hint creation, Key, review/export and restart recovery must work with all egress blocked. Preserve an already working route when another route is incomplete.
6. **Capacity:** compute unique missing model bytes (deduplicate shared dependencies) + cache/partial duplication + extraction/installation staging + old/new versions during repair/update + a stated reserve **per destination volume**. Separately estimate movie copy/extracted frames, masks, runtime intermediates and each output's storage for the selected range. Show required/free bytes for app, model/cache, scratch and output volumes, including UNC/NAS failures. Existing `~5/~6/~37 GB` labels and 10% download headroom are estimates, not a full release disk requirement. Final totals come from the catalog and measured scratch/output cases.

### Installer lifecycle and compatibility details for L7

- **Locations/relocation:** app binaries/runtime are versioned installation-owned data; projects, outputs, models and settings are separate user data. Resolve install-relative runtime paths at launch rather than baked build paths. A managed Python/venv is not assumed movable: relocation must either use a proven relocatable bundle or recreate/repair interpreter paths from pinned offline payloads. Move app/model roots through the installer/Settings, preserve old state until validation succeeds and update shortcuts/receipts atomically. Never recursively replace a user-selected arbitrary directory.
- **Hardware:** record Windows/Linux architecture, OS/glibc where applicable, GPU name/compute capability/VRAM, NVIDIA driver, pinned torch/CUDA wheel runtime, torchvision, OpenEXR and codec support. Reuse `verify_torch_runtime.py`; probe actual allocation/kernel work and representative loads. Test each model family, not just `torch.cuda.is_available()`. Bundled CUDA wheel runtime does not imply a system CUDA toolkit requirement. Unsupported drivers/devices get exact diagnostics; no silent CPU fallback for CK2. The Windows torch 2.11/cu130 smoke environment is not the release dependency pin (source currently pins torch 2.9.1/cu128 install paths).
- **Update:** fork automatic updates are currently disabled; add explicit local update/repair for this fork's own artifacts, with pinned verified manifests, stage-before-switch, retained previous runtime/catalog and rollback on launch validation failure. Never `git pull` a packaged install or rebuild its live environment in place. Preserve jobs/settings/models and migrate schemas with backup; retain old model revision while old jobs need it.
- **Uninstall/repair:** receipt tracks only owned files, shortcuts and later app-owned service/firewall resources. Default removal leaves projects, exports, models and preferences. Offer separately enumerated data removal only explicitly; never follow symlinks or wipe a shared HF cache. Repair reuses valid assets and offline payloads, reports inaccessible user data, and does not recreate all models or erase working environments.
- **Diagnostics:** record artifact/runtime/catalog versions, readiness and redacted logs locally; no mandatory telemetry/login/online version check. Install completion has a machine-readable result and a visible summary. Include relevant license notices; distribution remains blocked until the audit resolves this private fork's stated no-redistribution policy and component-specific terms.

## 7. After gate L: persistent remote work

### R0 — move scheduling ownership once

Extract the existing scheduler core into the smallest local coordinator process; keep its state transitions and worker protocol. Persist job snapshots/dependencies/terminal outcomes and event position with atomic state/journal operations; adopt a database only if measured requirements demand it. The desktop becomes a client of this coordinator, never another dispatcher. Initially use local IPC without a TCP listener; the coordinator and local workers remain usable without a network.

Add authenticated reconnect, replay/query by stable job ID, idempotent submit, coordinator/worker identity, attempt/fencing tokens, ownership checks and manifest reconciliation. Workers own one active job, survive UI disconnection as specified and expose authoritative status. Connection loss is not proof a writer died; heartbeat expiry cannot release a lease or cause a duplicate dispatch. Kill/restart coordinator and worker separately and prove recovery before enabling auto-placement.

### R1 — installed network roles and least-privilege startup

Add installer roles **Local desktop (default)**, **Coordinator**, **Worker**, and combinations only after R0. Install narrowly scoped Linux user/system services or Windows service/task under a known account as required by the role. Document startup at login versus boot, model/cache/scratch ACLs and clean stop/update/uninstall. A boot worker must not depend on an interactive drive mapping, SSH agent, login-only Tailscale route or the GUI staying open. Preflight network/storage in the actual service account/session.

Reuse authenticated system SSH transport where it satisfies the persistent role design. If a new listener is necessary, first specify its single purpose, authentication/pairing, encryption, authorization and exact port(s). No fixed new port is chosen in this design task. Never bind an unauthenticated job/file/diagnostic endpoint to all interfaces. Pairing/auth failures are visible and logs redact credentials; SSH host-key verification stays enabled. Local and remote worker model identities derive from the catalog, so remote capability checking must not require an unrelated local GPU to be Ready.

**Firewall contract, both OSes:** local role opens nothing. At the explicit Enable network role step, show the exact executable/service, direction, protocol/port, bind address/interface and allowed peer addresses. Windows rules use the intended program/service, exact port and Private profile; Tailscale gets explicit overlay interface/peer scope and must not rely on a broad Public-profile exception. Linux modifies only the detected active firewall manager, with scoped source/interface/port rules; no global policy changes, disabling firewall, opening an arbitrary port range or guessing overlapping managers. No inbound model-download rule. If authentication, network scope or privileges are unavailable, report incomplete network setup and leave local use working. Record app-owned rule IDs, remove only those on role disable/uninstall and preserve pre-existing SSH/Tailscale policies.

LAN and Tailscale are separate selectable connection routes to a stable worker identity. Detect duplicate registration of one host/GPU over both routes; switching addresses must not create a second GPU owner. Tailscale installation/account enrollment and NAS credentials remain explicit machine administration, never guessed or written to chat/project JSON. Connection tests distinguish DNS/routing, host identity/auth, protocol, GPU/model readiness, storage and publication failures.

### R2 — per-worker path mapping and storage proof

Extend the **existing** multiple Add/Remove mapping rows, rather than adding a competing mapping store. Each worker owns its rows. Display UI path → worker path, examples in each OS's syntax and a dry-run preview for source/hint/output/manifest paths. Include both directions of deployment: a Windows UI `Y:\` can map to Linux `/mnt/Projects`; a Linux UI `/mnt/Projects` can map to Windows `Y:\` **only if that worker/service session sees it**, otherwise a validated UNC root. Add a second independently used row (for example `X:\Shots` ↔ `/mnt/Footage`) in acceptance; testing only one row misses ordering/coverage bugs.

Use longest matching **whole-component** prefix, source-OS separator/case semantics and destination-OS validation; reject conflicting equal-prefix rows, `..`, unhandled paths and source/output overlap after mapping. Do not use the UI host's filesystem parser to interpret foreign paths. Keep stable logical job/clip identity separate from each host's physical path and map returned manifests/events to local-readable paths. Map external referenced sequences and hint paths too: remapping `clip_root` alone does not rewrite absolute paths stored inside `clip.json`.

Before dispatch, the worker opens the exact source/hint assets and validates a safe temporary write/no-clobber capability under each mapped output root using its real service identity. Prove shared storage identity with an explicit app-owned round-trip marker/hash, not similar filenames. Keep backend containment/symlink protection and exclusive publication checks. Current hardlink-based publication must either pass on the target share or fail clearly before inference; no check-then-overwrite fallback. Store no NAS password in mappings. Windows NAS auth remains a blocker until the chosen account has working access; do not claim `Y:\` or UNC syntax alone solves authentication.

Shared-storage operation is the first remote acceptance target. If a selected worker has only local disk, either label that target unsupported for shared jobs or implement an explicit staged transfer/import-back capability with checksums, resume, disk preflight, safe publication and cancellation before advertising it. The previous Windows local-disk smoke is not proof of cross-host transfer.

### R3 — actual UI-to-worker acceptance

Run the packaged **local UI**, persistent coordinator and actual installed remote workers. Required matrix: Windows UI ↔ Linux worker and Linux UI ↔ Windows worker, each over LAN and Tailscale; include mixed-worker batches and a second distinct mapping row that is actually used. Capture connection route/role account, worker/GPU identity, catalog/protocol versions, mapping previews, source/outputs and artifacts. A CLI hello or synthetic mock is supplemental evidence only.

Verify UI submit→accepted→phase progress→live output→complete, queued dependencies, target/Auto selection, cancellation/Resume, failed prerequisite, wrong model/protocol, wrong/uncovered path, inaccessible share, host-key/auth/firewall denial, UI close/reopen, coordinator restart, worker reboot, route loss/reconnect and source/NAS outage. Prove no duplicate job on address changes, no overwritten outputs and no automatic lock theft. Test firewall enabled/disabled role transitions, rejection from an unauthorized peer/Public network and cleanup on uninstall. All tests require scoped authorization and isolated test data when that phase begins; do not modify the user's current firewall or NAS configuration as part of planning.
